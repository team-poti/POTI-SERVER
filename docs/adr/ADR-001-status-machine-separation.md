# ADR-001: 상태 머신 분리 설계 (GroupBuyPostStatus / OrderStatus)

**상태:** 채택됨  
**결정일:** 2026.01

---

## 컨텍스트

포티의 핵심 가설(H2)은 "채팅 없이도 상태 관리 UI만으로 분철 진행 상황을 전달할 수 있다"는 것이다. 이를 실현하려면 **상태가 명확하고 역할별로 분리**되어야 한다.

문제는 모집자(총대)와 참여자(구매자)가 동일한 거래를 서로 다른 관점으로 본다는 점이다.

- 모집자는 분철글 전체의 진행 단계를 본다 (모든 참여자가 입금했는가? 모두 배송됐는가?)
- 참여자는 자신의 주문 상태를 본다 (내가 입금했는가? 내 배송이 출발했는가?)

하나의 Enum으로 통합하면 두 관점을 하나의 값으로 표현해야 하므로 서비스 계층의 분기 로직이 복잡해지고, 디자인도 이미 두 화면을 분리해 설계하고 있었다.

---

## 결정

상태를 두 개의 독립적인 Enum으로 분리한다.

- **GroupBuyPostStatus**: 분철글 전체의 진행 단계 (`RECRUITING` → `CLOSED` → `PAYMENT_DONE` → `SHIPPING` → `DELIVERED`)
- **OrderStatus**: 개별 주문의 상태 (`WAIT_PAY` → `WAIT_PAY_CHECK` → `PAID` → `SHIPPED` → `DELIVERED`)

자동 전환 원칙: 해당 분철글의 **모든** Order가 특정 상태 이상이 되면 GroupBuyPostStatus가 자동으로 다음 단계로 전환된다.

---

## 이유

- 두 역할의 관심사가 근본적으로 다르므로, 도메인 모델이 이를 반영하는 것이 자연스럽다.
- 억지로 통합 시 모든 API·서비스에서 "이 사용자가 모집자인가 참여자인가"를 판단하는 분기가 추가된다.
- H2 가설 검증을 위한 상태 시각화 UI가 정확히 작동하려면 상태값이 명확해야 한다.

---

## 결과

- 모집자 화면: GroupBuyPostStatus 기준으로 상태 표시
- 참여자 화면: OrderStatus 기준으로 상태 표시 (CLOSED까지는 GroupBuyPostStatus 우선 적용)
- 서비스 계층에서 count 쿼리로 자동 전환 조건 판단
- `OrderStatus.RECRUITING` 값은 데모데이 목적으로 추가되었으나 PR #208(상태값 재정의)에서 제거 완료
